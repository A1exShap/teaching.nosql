# Примеры кейсов, в которых применяются графовые БД
1. Рекомендательная система. Нужно найти фильмы, которые понравились друзьям пользователя, но он их ещё не смотрел. В реляционной БД это требует множественных JOIN'ов таблиц friends и likes. При глубине 3+ (друзья друзей друзей) промежуточные результаты растут лавинообразно, и запрос деградирует.
2. Обнаружение мошенничества. Поиск «колец» аккаунтов, связанных общими атрибутами (телефон, карта, IP). В графе это поиск паттернов (циклов) одной Cypher-конструкцией. В SQL это рекурсивные CTE или многоуровневые подзапросы, которые сложно писать и тяжело оптимизировать.
3. Управление доступом. Проверка, имеет ли пользователь доступ к ресурсу через цепочку групп и ролей. Глубина вложенности групп может быть большой. Граф проходит эту цепочку за один обход, реляционная БД — за серию соединений или требует материализованных путей.

## Разберем отличие между графовой (Neo4j) и реляционной (PostgreSQL) БД на примере рекомендательной системы.
# Сравнение моделей данных
## Модель данных в Neo4j
- Узлы: User (свойства: name), Movie (свойства: title).
- Связи: (:User)-[:FRIEND]->(:User), (:User)-[:LIKED]->(:Movie).

## Модель данных в реляционной БД
- Таблица users (id, name).
- Таблица movies (id, title, description).
- Таблица friendships (user_id, friend_id).
- Таблица likes (user_id, movie_id).

# Сравнение запросов
## Запрос в Neo4j (Cypher)
MATCH (alice:User {name: 'Alice'})-[:FRIEND]->(:User)-[:FRIEND]->(fof:User)-[:LIKED]->(m:Movie)
WHERE NOT (alice)-[:LIKED]->(m)
RETURN DISTINCT m.title

## Запрос в PostgreSQL
SELECT DISTINCT m.title
FROM likes l1
JOIN friendships f1 ON l1.user_id = f1.friend_id  -- Фильмы, которые лайкнул друг
JOIN friendships f2 ON f1.user_id = f2.friend_id  -- Друзья друга
JOIN likes l2 ON f2.user_id = l2.user_id                -- Что лайкнули они
JOIN movies m ON l2.movie_id = m.id                 -- Получаем название
WHERE f2.friend_id = (SELECT id FROM users WHERE name = 'Alice')
  AND m.id NOT IN (SELECT movie_id FROM likes WHERE user_id = (SELECT id FROM users WHERE name = 'Alice'));

В данном примере показан запрос для второго уровня друзей (друзья друзей).
Если нужно получить данные то 3 уровню, то придется добавить ещё два JOIN (f3, l3). Количество промежуточных строк, которые СУБД должна перебрать, вырастет экспоненциально.
В графе добавление одного уровня — это ещё один -[:FRIEND]->, и время вырастет линейно.

# Преимущества Neo4j
- Читаемость и декларативность. Cypher-запрос визуально повторяет структуру графа.
- Добавление ещё одного уровня связей (друзья друзей друзей) не требует переписывания запроса — только добавления одного сегмента в паттерн. В SQL это означало бы переписать весь запрос и добавить новые алиасы таблиц.
- Производительность на глубоких связях. За счёт указателей между узлами обход графа не требует построения индексов для каждой связи.
